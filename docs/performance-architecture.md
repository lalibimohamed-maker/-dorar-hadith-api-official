# بنية الأداء السريع

الهدف ليس استبدال JavaScript بل منع ارتباط سرعة الموسوعة بوقت تشغيل واحد.

## المبدأ

المستخدم يرى خدمة واحدة. داخليًا تُستخدم طبقة Orchestrator تختار أفضل runtime أو تشغّل عدة adapters بالتوازي حسب المهمة والصحة والكمون.

المهام المستهدفة:
- search: بحث منخفض الكمون مع إلغاء المهام البطيئة.
- reader: cache + streaming/range delivery بدل تحميل الملف كاملًا قبل العرض.
- download: استئناف وتقسيم الملفات عند دعم التخزين/البروتوكول.
- voice: طوابير معالجة غير متزامنة وcache للنتائج المتكررة.
- video: pipeline غير متزامرة، ترميز متعدد الدقة وadaptive streaming؛ لا نعد بأن 4K سيعمل بسرعة دون توفر المصدر/العتاد/الشبكة.
- OCR: workers مستقلة ومتوازية مع حدود موارد واضحة.

يمكن لاحقًا إضافة runtimes مثل Node.js أو Go أو Rust أو Python بحسب benchmark الفعلي. لا يتم اختيار لغة لمجرد اسمها؛ القرار مبني على قياس throughput وp95 latency واستهلاك الذاكرة وتكلفة التشغيل.

## الحوكمة

الـOrchestrator لا يتجاوز حقوق المصادر ولا يكتب مباشرة إلى Corpus. الأداء طبقة تنفيذ فقط، بينما Provenance/Rights/Validation تبقى بوابة مستقلة.

## أهداف أولية

- budget افتراضي للعمليات التفاعلية: 1800ms.
- حتى 8 workers/adapters في التنفيذ المتوازي للمهمة الواحدة.
- إلغاء النتائج البطيئة عند توفر نتيجة مقبولة، حيث يسمح المسار.
- cache وstreaming هما جزء من الأداء، وليس زيادة عدد اللغات فقط.
